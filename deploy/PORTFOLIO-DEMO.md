# Synthetic portfolio demo

Use a separately approved, fresh disposable deployment. Never attach the existing
local demo PostgreSQL volume, import personal data or publish test credentials.
The automated entry today is the manual Candidate frontend Chromium E2E workflow;
its validated source-built frontend is distinct from the published v1.0.0 frontend.
Frontend v1.0.1 is not published yet. After publication, use its verified registry
digest in a separately reviewed overlay; do not claim that deployment exists today.

For an operator-supervised browser demonstration with protected synthetic accounts:

1. Open the loopback frontend in Chromium. Register a synthetic Merchant at
   /merchant/signup, verify validation/pending approval, and sign in.
2. In a separate authorized Admin session, review and approve that Merchant through
   the Admin UI. Return to the Merchant dashboard and verify eligibility.
3. Create a small synthetic payment, process it explicitly and inspect its history.
   Explain currency routing and idempotency without calling a real provider.
4. Record partial then remaining full refunds; distinguish recorded refund totals,
   potential eligibility and bank settlement. No bank arrival is claimed.
5. Create a separate synthetic payment link. Open the token checkout in an
   unauthenticated context, review and confirm simulated payment, then verify receipt
   and Merchant status. Never include the token URL in public logs or screenshots.
6. Run explicit investigation and knowledge chat. Explain Java's authorized evidence
   boundary, Python retrieval, local Qwen structured selection and strict validation.
   Confirm real inference through sanitized evidence rather than a success label alone.
7. Rename, list, load and refresh a test conversation. Demonstrate owner/role isolation,
   delete only the conversation created for this demonstration, then log out and
   verify protected-route/session invalidation.
8. Teardown only the unique disposable project's resources through the guarded
   procedure and verify containers/volumes are absent.

No real payments, card/UPI credentials, paid APIs or production data are involved.
The current Chromium suite validates this bounded journey but is not a broad WCAG
or visual-regression audit. Preserve source-available and third-party notices.

Interview summary: Java owns financial transactions, authorization and persistence;
Python receives minimized evidence and cannot mutate financial tables. Exact money,
request identity, outcome uncertainty and evidence-grounded AI are enforced outside
the model. The frontend's saved-history fix was verified through real Chromium,
while immutable artifact identity and cleanup are checked separately from UI success.
